# number-theory

A library of number theory papers whose results are checked by the Lean 4 kernel.

- `lib/`: the Lean library, built with Lake against Mathlib.
- [`formalisations/`](formalisations/README.md): one note for each published result that the library formalises.
  Each note gives the result's source and attribution, and any differences between the Lean statement and the
  published one.
- [`papers/`](papers/README.md): the papers. Each claims only its own steps and cites `formalisations/` for the
  results it uses.

The first paper is on [Linnik's exponent](papers/linnik-exponent/README.md), which bounds the least prime in an
arithmetic progression.

## Layout

| Path | Contents |
|---|---|
| `lib/core` | The library's modules that need only Mathlib: 349 files. |
| `lib/pnt` | The modules that also use PrimeNumberTheoremAnd, among them the Linnik paper's: 747 files. |
| `lib/dh` | The Davenport–Heilbronn function and its zeros: 53 files. |
| `lib/zeta23` | The modules that also use `zeta23`: 11 files. |
| `lib/vendor/pnt-plus`, `lib/vendor/zeta23` | Two upstream libraries, ported to this toolchain, each with its license and its port patch. See their READMEs. |
| `lib/check/Check.lean` | The axioms of the papers' theorems. This is the default build target. |
| `lib/check/CheckAll.lean` | The axioms of every final theorem of the library. Not built by default. |
| `formalisations/` | The notes on the results from the literature. See its [README](formalisations/README.md), the index of the notes. |
| `papers/` | The papers. See its [README](papers/README.md). |
| `scripts/` | The checks below, `build.sh` and its wrapper `lean-slots.sh`, the generator of `lakefile.lean`, `import_cone.py` (the import cone of a module, with the certificate parts in it), and `build_site.py`, which builds the papers' web site. |
| `docs/` | [`dry-efficiency-survey.md`](docs/dry-efficiency-survey.md): the survey of duplication and build cost behind the DRY / efficiency pass, with what was and was not done. [`stack-bridges.md`](docs/stack-bridges.md): three small modules that join parts of the library with no import between them. |
| `tools/linnik/` | The Linnik paper's certificate tools: the route's computations outside Lean and the generator of the certificate's Lean files. See its README. |

The module names are flat (`import SieveMain2`). `lakefile.lean` is generated by `scripts/gen_lakefile.py` and names
every module of each layer, because Lake's globs cannot select a directory of flat module names. Regenerate it after
adding, removing or renaming a module.

## Building

You need [elan](https://github.com/leanprover/elan), git and Python 3. `lean-toolchain` pins Lean v4.35.0-rc3, and
`lakefile.lean` pins Mathlib at `0f64d30a9a4593b3ae50375b960a5cf7f0845606`.

```sh
lake exe cache get               # Mathlib's prebuilt files
scripts/build.sh                 # lake build, at most two certificate parts at once (see Memory)
python3 scripts/check_axioms.py  # the axioms of the papers' theorems
```

`scripts/build.sh` builds the default target, `lib/check/Check.lean`, and everything it imports. A plain `lake build`
builds the same thing where memory allows. The two produce the same build, so either can continue the other's.
If Mathlib's cache does not have the pinned commit, `lake build` builds Mathlib as well, which takes several hours.

**Memory.** A module that imports Mathlib maps Mathlib's files into memory, and that mapping is shared between
compiles. The default build also has 143 certificate parts (`lib/pnt/SieveCert22322RP<k>.lean`). Of Mathlib the parts import only
`Mathlib.Data.Nat.Notation`, but each one can use about 5 GiB of private memory while the kernel checks it. Earlier
certificates (for the weaker exponents `899/400`, `9/4`, `226/100` and others) and the stepping-stone modules only they used are
no longer in the tree; they are in the git history. Lake runs about as many
compiles at once as there are cores, so a plain `lake build` on a machine with less than about 5 GiB of memory per
core can run out while it builds the certificates. `scripts/build.sh` runs Lake with a wrapper
around `lean`, `scripts/lean-slots.sh`. The wrapper allows at most `LEAN_SLOTS` compiles at once (default: the
number of cores) and at most `LEAN_HEAVY` certificate parts among them (default 2). It also deletes each module's
setup file after its compile; Lake writes that file for the compile and does not read it again. It needs `flock`.
On 4 cores and 16 GB, a cold build of the default target takes several hours. Two certificate parts at once can come
close to the limit of a 16 GB machine: a compile killed with exit code 137 has run out of memory, and
`LEAN_HEAVY=1 scripts/build.sh` finishes the build, keeping what is already built.

## Checks

| Command | What it checks |
|---|---|
| `python3 scripts/check_axioms.py` | After `lake build`: every theorem in `lib/check/Check.lean` depends only on `propext`, `Classical.choice` and `Quot.sound`. With `--all` it checks `CheckAll.lean` instead, which must be built first with `lake build CheckAll`. |
| `python3 scripts/check_hygiene.py` | The library's own sources contain no `sorry`, `admit`, `native_decide`, declared `axiom`, `implemented_by`, `extern`, `unsafe`, `ofReduceBool`, `skipKernelTC` or `#exit`. |
| `python3 scripts/gen_lakefile.py --check` | `lakefile.lean` matches `lib/`. |
| `python3 scripts/check_vendor.py` | `lib/vendor` holds the upstream files at the pinned commits with the port patches applied (needs network access). |
| `python3 scripts/census.py MODULE CONSTANT` | After `lake build MODULE`: the library's modules whose declarations the proof of `CONSTANT` uses, with the count from each. |
| `python3 tools/linnik/check_certificate.py` | The certificate's Lean files in `lib/pnt` are the ones `tools/linnik` generates (about two minutes). |
| `python3 scripts/import_cone.py [ROOT]` | Not a gate: the modules, source size and certificate part files in the import cone of `ROOT` (default `Check`, the default build), from the sources alone. `--why MODULE` prints the chain of imports that puts `MODULE` in the cone. |

## CI

`.github/workflows/ci.yml` runs on pull requests and on pushes to `main`:

- **Checks:** `check_hygiene.py`, `gen_lakefile.py --check`, `check_vendor.py` and `check_certificate.py`.
- **The papers:** every `papers/<name>/main.tex` is compiled with LaTeX, and the PDFs are kept as an artifact.
- **The Lean build**, with a cache. On a pull request it runs only if the pull request changes `lib/`, the Lake
  files, `lean-toolchain`, the build scripts or the workflow; on pushes to `main` it always runs. Mathlib's prebuilt
  files come from Mathlib's own cache (`lake exe cache get`).
  The library's build directory, `.lake/build`, is restored from the GitHub Actions cache and saved back after
  every stage, including a stage that fails or is cancelled. Lake then rebuilds only what changed. A cold build
  takes longer than one job may run (six hours), so the build runs in up to three chained stages, each continuing
  from the previous stage's cache. The stage that finishes the build runs `check_axioms.py`.

The job **CI passed** summarises the others: it passes when each passed or was skipped, and fails if any failed or
was cancelled. It is the check that `main`'s branch protection requires, so a pull request merges only when CI is
green or skipped throughout. A new job must be added to its `needs`.

`.github/workflows/pages.yml` runs on every push to `main` that changes `papers/`. It compiles every paper and
publishes the PDFs, with an index page built by `scripts/build_site.py`, to GitHub Pages:
<https://dickie81.github.io/number-theory/>. The Linnik paper is `linnik-exponent.pdf` there.
